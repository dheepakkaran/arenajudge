The bug hunt

  1. Symptom

    Some batches were about — slower per layer.

  2. Cause

    Qwen2.5 uses grouped-query attention: — query heads share — key/value heads. When every sample hit the —-token cap there was no padding, a different code path skipped expanding the key/value heads, and PyTorch silently fell back to a slow unfused kernel.

  3. Fix

    Pad every batch to a multiple of 8 tokens. —.

    Shrinking it for a free CPU

    A free live demo can't use a GPU, so the model had to run on a plain CPU. I tried — engines.

    Lesson: quantize the weights, not the activations. Plain INT8 also squeezes the activations (the numbers flowing between layers), and LLM activations have big outliers. Weight-only 4-bit keeps them at full precision: same accuracy as fp32, — smaller.

    ONNX Runtime on its own was — faster than PyTorch on CPU, with the same log loss.

    What I learned, and honest limitations

    What I learned

    • Measure first. Most “obvious” speedups (bigger batches, pinned memory, torch.compile) did nothing here. The profiler showed why.
    • Silent slow paths are real. A missing bit of padding sent attention to a kernel about — slower, with no warning.
    • Quantize weights, not activations, for LLMs on CPU.
    • Containers lie about CPUs. os.cpu_count() sees the host, not your quota.
    • Rank isn't fully in your control; score is.

    Honest limitations

    • It predicts what humans prefer, not what's correct. Humans also like longer answers.
    • It only sees the first — tokens of each answer.
    • Top teams use much larger models and ensembles; this is a 1.5B model built on free GPUs.
    • CPU numbers come from a small —-row check; live latency depends on input length and the Space's hardware.
    • The free Space sleeps when idle; the first visitor after a while waits about 1–3 minutes.

    Next: a v2b model that reads longer answers (— tokens) plus each answer's word count, and a resubmit before the 2-month rolling window drops the best version.
